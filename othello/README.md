# オセロ: プレイヤー vs Ollama AI

Jev 代替決定モデル評価(`jev-eval`)の一環として、Ollama 上のモデル(decision / baseline
いずれも)を相手にオセロを対戦できるようにしたもの。盤面の評価自体はコード側の探索
(`search.py`)が行い、その結果を `runner.ask()` / `runner.ask_baseline()` の
`questions` (type: `choice`) に criteria として渡して、モデルにキー(例 `"d3"`)を
選ばせる。モデルの役割は「オセロを考えること」ではなく「コードが計算した評価値を
正しく読み取って選べるか」という分類寄りのタスクである点に注意(詳しくは検証メモ参照)。

## 起動方法

```bash
cd /Users/kosuke/projects/work/jev-eval/jev-eval
.venv/bin/python othello/app.py
```

ブラウザで http://127.0.0.1:5050 を開く。色とモデルを選んで「新しい対局」。

## 構成

- `engine.py` — オセロのルール(合法手判定・着手適用・終局判定)と位置重みテーブル。外部依存なし。
- `search.py` — negamax + alpha-beta によるヒューリスティック探索(盤面の分岐数に応じて深さ
  3〜5を自動調整)。空きマスが10以下になったら、ヒューリスティックではなく石差を完全に
  読み切る厳密解(`exact_solve`)に切り替わる。
- `ai_player.py` — `search.py` の評価値を `state`/`questions` に変換し、`runner.ask`/
  `ask_baseline` を呼んで AI に一手を選ばせる。不正な応答や通信エラー時のフォールバックは、
  ランダムではなく探索上のベストムーブ。
- `app.py` — Flask サーバー。1 プロセス = 1 対局のシンプルなサーバー側グローバル状態。
  プレイヤーの着手は `/api/move` で即座に反映し、AI の着手は `/api/ai_turn` で別リクエスト
  として進める(プレイヤー自身の着手結果を待たせないため)。
- `templates/`, `static/` — 盤面 UI (fetch ベース)。対局ログのクリップボードコピー、
  直前の着手のハイライト表示、選択モデルの localStorage への保存に対応。

## モデル比較の観点

AI が着手するたびに `latency_s` と `confidence`(decision モデルのみ)を画面下のログに表示
する。実際に対戦・リプレイ解析した結果、モデルの強さの差は「オセロの戦略理解」ではなく
「コードが計算した評価値(どれが最善手か)にどれだけ忠実に従えるか」という指示追従性・
キャリブレーションの差として現れることが分かった(nimble は高確信度でほぼ完全に追従する
一方、tev1:0.8b は中盤の分岐が広い局面で推奨から逸脱し、評価値が大きく悪化する事例を確認)。
詳細は検証メモ(Notion)を参照。

## 既知の限界 / 今後の拡張案

- 空きマス10を超える局面の評価はヒューリスティック(位置重み+モビリティ差)止まりで、
  終盤の完全読み切りと比べると見通しが浅い。Claude in Chrome が独自に構築した「モビリティ差
  + 残り12マスからの完全読み切り」エンジンに、こちらの探索(当時はexact solve未実装)が
  61-3 で大敗した実例があり、この閾値をさらに引き上げる余地がある(現状は Python の素朴な
  alpha-beta のみで空き10を閾値にしている。トランスポジションテーブル等で高速化すれば
  より深い閾値でも実用速度に収まる可能性がある)。
- 複数モデルの AI 同士を自動対戦させて勝率・平均レイテンシを `results/` に集計するスクリプト
  (既存の `run_eval.py` と同様の構成で作れる)。
