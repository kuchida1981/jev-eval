# Jev 代替決定モデル ローカル評価 — Phase 2 サマリー

Phase 1([Notionの既存サマリー](https://app.notion.com/p/41683feb3753817e9331f81409c4005b))の結果を前提に、公平性の検証・ラベル監査・頑健性追試・資源計測を行った。各セクションの詳細は `results/phase2/step*.md` を参照。

## Step1: 共通問題セットでの公平比較 + 180秒再実行

- qwen3.5:9bがタイムアウトした7件を除外した共通41件セットでも、モデル順位(qwen3.5:9b > nimble > tev1 > tev1:0.8b)は変わらず、差分は±0.03以内。
- 7件を180秒タイムアウトで再実行したところ**全件が60〜82秒で完了**(180秒には遠く及ばず)。60秒という打ち切り設定が「根本的に無理」ではなく「わずかに足りなかった」ことが判明。48件全体を揃えた場合の qwen3.5:9b の正解率は **0.820**(元の0.827とほぼ同水準)で、結論への影響はない。

| model | 全件(timeout除外) | 共通41件 | 48件(180秒再実行込み) |
|---|---|---|---|
| nimble | 0.795 | 0.817 | 0.795(変更なし) |
| qwen3.5:9b | 0.827 | 0.827 | **0.820** |
| tev1 | 0.705 | 0.731 | 0.705(変更なし) |
| tev1:0.8b | 0.672 | 0.654 | 0.672(変更なし) |

## Step3: 安定性・頑健性追試

| 追試 | 結果 |
|---|---|
| a) 同一入力5回反復 | **完全に決定論的**(366組×5回、一致率100%・確信度分散ゼロ)。decision APIはサンプリングなし(temperature=0相当)。 |
| b) 質問文の言い換え2パターン | 全体 any_flip rate 0.134。**model_routingのみ突出(0.278)**し正解率も悪化方向。他タスクは0.06〜0.19。統計的有意差はなし(n小さく全てp>0.24)。 |
| c) model_routingのcriteria具体化 | flip rate 0.389→0.118、正解率(forward) 0.611→0.882 と改善傾向。ただしn=17〜18で95%信頼区間が重なり統計的有意差なし(McNemar p=0.13/0.48)。 |

→ **model_routingタスクは「選択肢順序」(Phase1追試)と「言い換え」(本追試)の2系統で独立して最も不安定と確認された、プロンプト表層に敏感なタスク**。criteria具体化は改善傾向にあるが、本番導入前に大規模な再検証が必要。

## Step5: 資源計測

- **コールドスタート**: nimble 5.49秒 / tev1 3.38秒 / tev1:0.8b 1.12秒(ウォーム時の25〜34倍)。16GB VRAMに4モデル(合計23.3GB)は同時に収まらず、モデル切り替えのたびにコールドロードが発生しうる。
- **質問数スケーリング(1→64問)**: nimbleのみ57倍(0.16→9.17秒)と極端に悪化。tev1・tev1:0.8bは2.6倍程度に留まる。大量質問を1リクエストにまとめる用途では、精度優位のnimbleよりtev1系が有利になりうる。
- **同時実行数(1/4/8)**: concurrency 4→8でスループットがほぼ変わらず(例: nimble 6.63→6.66 req/s)、ウォーム単発レイテンシの逆数とほぼ一致。**サーバ側は実質的に並列処理していない**(llama.cpp系の`-np 1`制約がOllama経由でも引き継がれている可能性)。
- VRAM実測(`/api/ps`): nimble 9.58GB / tev1 5.60GB / tev1:0.8b 1.26GB / qwen3.5:9b 6.90GB。nvidia-smiによるクロスチェックは未受領。

## 総合的な示唆

1. Phase1の結論(nimbleが速度対精度で最良のバランス)は、共通問題セット・タイムアウト再実行のいずれでも頑健に再現された。
2. model_routingタスクは複数の独立した追試で一貫して「表層的なプロンプト変化に弱い」と確認された数少ないタスクで、本番投入前に criteria の具体化が優先対応事項。
3. decision モデルは完全に決定論的なため、多数決による頑健化は無効。頑健性を上げるには入力・プロンプト設計そのものの改善が必要。
4. レイテンシ面では「質問数を増やす」場合にnimbleだけ急激に悪化し、「同時リクエスト数を増やす」ことはスループット改善に寄与しない。本番設計では、モデル選定だけでなく「1リクエストにまとめる質問数」と「並列化よりモデルインスタンス数を増やす」方針の検討が必要。
5. ラベル監査で2件の gold 修正候補が見つかった。反映前にユーザー確認を推奨。
